# 核心信念

这里记录的是协作方式上的通用信念，而不是具体方案结论。

## 1. 先写清楚问题，再开始实现

如果问题定义、目标、边界和验证方式还没有写清楚，就不应让实现细节代替设计文档。

## 2. 未确认的内容宁可留空

空白比伪确定性更安全。对未确认内容，应明确标记为“待定”“待验证”或“候选方案”。

## 3. 设计应服务于产品主张

任何技术方案都应回到核心问题：它是否真的帮助用户在多 Agent 协作中看清全局。

## 4. 计划可以推进设计，但不能替代设计

`ExecPlan` 可以用于设计阶段的探索、验证和推进，但计划本身不是设计结论。涉及问题定义、边界、候选方案和当前结论时，仍应回写正式设计文档；不要让里程碑、待办列表或实现顺序冒充架构结论。

## 5. 优先选择成熟规范的方案

验证工具应服务于当前产品风险。工具问题只有在影响本次判定或实验安全时才阻塞推进，通用健壮性不能不断扩成统一前置。预期失败或截断可以是场景通过，但验证该预期所需的证据不能缺失；局部自测数量不能替代整体执行路径和产品风险消减。

只要成熟、边界清楚、已经被广泛验证的方案能够满足目标，就不应为了局部新奇或一次性便利引入自定义机制。若决定偏离成熟方案，必须明确写清为什么成熟方案不能满足当前目标，以及偏离后的收益、代价和验证证据。

## 6. 文档是事实来源

如果某个结论只存在于实现细节、口头讨论或参考产品印象里，就等于它还没有被正式确认。

## 7. 平台支持必须和验证证据一起记录

代码路径已经接通，不等于平台支持已经完成。只要缺少对应平台的人工验证或可靠证据，就必须明确写成“验证中”或“待验证”。

跨平台实验也要验证夹具前提：创建了子进程不等于父进程退出后它仍存活，存活也不等于仍持有可写终端。平台的 Job、session leader 与终端撤销规则必须纳入对照；夹具前提失效不能冒充生产 reader 缺陷，也不能改标为产品已通过。

有界通道上的实验握手不能依赖“先写完全部内容，再开始读取”：写入可能需要消费进展才能返回，控制回执应独立于受测通道，并记录调用前后状态。前提定位与待测行为验收分别留证；修正探针不追认历史失败，失败工件也必须支持完整复核。

观察器的无侵入性必须覆盖启动链，而不只检查探针正文。继承或复制fd可能共享文件状态标志，启动库修改O_NONBLOCK会改变被观察reader；helper退出、身份/offset不变不足以排除干扰。应以原位只读观测和不传递受测资源的对照验证前提，前提失效时绿色样本也要限定结论。

控制进展不能依赖它正在等待的数据操作。写入回执、退出放行与读取循环应能独立推进，并通过暂停读取循环的受控场景验证因果顺序；一次顺利调度不构成保证。实验要求最小持有时间时应用单调截止点核对，定时器触发本身不是已经经过足够时间的证据。

底层诊断门槛不自动等于产品承诺。职责澄清后，应保留冻结实验、原始断言和失败，只重评其是否阻塞产品；不能为了口径收窄删除证据或追认通过。Terminal / Agent 会话不默认托管实际主进程退出后的普通后代，但主进程尾部、已进入链路的内容、最终终端状态和资源释放仍要验收；启动器启动的实际 CLI 是执行主体，不能用普通工具后代的边界排除。父子关系和前后台关系也不能混用。

取消的诚实分类不能代替完整性证明。保住已接收或在途读取的数据，仍不等于收齐系统缓冲中的尾部；诊断追加读取发现的数据必须单独计账，不能算作候选已经交付。单次资源关闭、自然进程结束也不代替长驻资源无增长验证。

资源稳定性必须在同一进程内跨多次生命周期观察，以预热基线、无资源创建对照及OS原始计数区分一次性初始化、持续积累和观测开销。能记录资源类型与身份时，不只保存总数；内容完整、JS回调收敛、驱动进程自然退出与native资源无增长分别判定。

资源归因干预必须控制重编译工具链和启动辅助程序，保留原包、重编译基线与最小干预的差异。句柄槽位不是稳定对象身份，取证竞争或访问失败须显式报告；基线失败与新对照结论分别保存。

类型查询成功而对象身份查询失败时，可以分别保留已确认的类型事实与未闭合的归属问题；不能为了统一绿色而忽略查询错误，也不能把完整性通过或已退出进程对象误写成资源已释放。

Windows已退出进程被句柄引用而继续保留对象是正常语义，不等于进程仍运行或系统泄漏。缺陷判断必须另外证明调用方的资源所有权、保留用途与最终释放责任；只关闭已知owner，不能强杀或盲关陌生句柄求计数归零。

部分创建路径的子进程可能在真正执行目标程序前就以非零状态退出；`kill` 返回0只证明信号请求被内核接受，不要求随后一定以该信号结束，也不替代wait结果、owner登记或资源结算。退出形式不能单独作为资源unknown、系统缺陷或准入成功的判据。

场景符合预期、资源已结算和证据充分应分别判断；整体通过要求三者成立，继续有限诊断样本要求资源与证据均成立。内容或预期退出不符不自动抹去真实资源返回，通知与raw矛盾也不能用场景命中掩盖。判据修订使用新版本与新输入，旧失败、未运行项及入口错误保持原记录，不合并新旧通过率。

部分创建失败只结算实际取得的资源：已取得TSFN但线程未创建时，必须证明TSFN Release/finalizer和child回收；未创建的thread、payload、notification不需要虚构join、释放或回调。唯一创建者的WNOHANG返回0或EINTR仅为pending，不解释status；只有属于本child的真实终态才能证明已回收。

合成等待失败的首次未确认事实与后续真实终态必须分开保留，不能用后来成功覆盖原错误，也不能解释无效status为exit0。只有明确跳过系统调用的注入才具有随后首次真实wait的前提；真实ECHILD不因此获得重试依据。原生发布和JS观察分属不同时刻，JS晚读到首报不代表观察当时仍未退出，不为没有先观察要求的实验另增门控。

HPCON 是 opaque owner token，不是可用 CloseHandle 释放的普通 Win32 HANDLE。只有同一诊断模块创建并仍持有的 token，才允许在真实 pipe EOF、消费者完成和 shell 退出后由唯一主线程调用一次 ClosePseudoConsole；PtyKill、TerminateProcess、陌生句柄和过早 Close 都不能作为自然收尾。

资源因果对照还必须隔离工具本身的差异：stock 不调用候选 API，同工具链候选共享编译产物；原生等待、TSFN 和一次性连接前提失败时，不能依靠 JS 调用顺序补造成功。void 导出调用返回只证明本次调用返回，不证明 OS 已经销毁全部关联对象。

资源总量应区分显式owner引用、预热期间形成的背景和逐会话增量。普通进程控制中的退出后image31、释放23个引用后总数下降23与未知背景+5可以同时成立；保留原计数失败，不以事后换基线替代归属证据。

同一native上的已知owner释放干预可以建立正常路径的窄因果证据，但不能自动证明每个内核对象的类型、全局引用消失、异常/取消路径或生产适配层已经正确。候选消除逐会话增长时，仍保留no-close正对照的原始失败与稳定背景；正常Windows对象语义和调用方最终Close责任并不矛盾。

诊断的硬返回必须独立于被等待对象的stdio生命周期。向child发送kill不保证child.close按时发生，已经退出的driver仍可能留下被其他进程持有的stdio；应分别记录exit、close、超时分类与已知资源清理。没有触发watchdog的自然成功样本不能证明硬截止有效，工具预算控制也不能冒充对应平台的产品故障复现。

跨平台夹具必须证明操作实际生效；close调用返回与通知到达顺序不证明句柄已经关闭时OS主体仍存活。标准句柄的特殊处理、系统退出与JS回调调度须分别取证；校验器漏掉前提时保留原pass，并明确对应场景未覆盖，不改写整个平台或全部控制结果。

要证明资源关闭后主体仍可执行，应在观察到关闭后才生成新的私有挑战，由同一受控主体经独立通道响应；预先准备的token、PID或关闭自报都不能替代。要求持续存活窗口时，从有效响应的单调时刻计时并再次挑战，以保持资源开放和关闭后立即退出两类负控验证oracle；任何失败都不自动成为有意负控通过。补证采用新输入/工件，旧前提缺口不追认。

跨层收尾应分开实际主体终止、可信源结束、权威终端解析、各读者应用及资源处置。共享adapter串行接受数据并唯一分配序号，authority的journal入队/flush不能替代异步tracker解析，Webview的最终revision只覆盖权威stream而非其后追加的本地退出提示。源水位、命令退出码和页面完成互不代证。

unknown/unconfirmed是带时间的观察；同一执行/代际/操作的迟到证据可补足当前状态，但不能覆盖首次超时报告、重发旧封口或重复释放。native逐项owner与页面/journal寿命分离，所有权移交尚未验证时，不把诊断consumer-before-Close门槛直接改写成已证明的生产偏序。

诊断控制正确识别故障可以通过，但被测路径的超时、截断和未知仍须保留。超时后通过协作或强制控制得到的管道end不将整次采集升级为自然完整；启动失败后的空捕获通道可以完整结束，也不能反推进程创建成功。校验器应从原始事件和单调时钟重算，而不是信任pass字段或模型自报。

读者释放只有携带有效最终应用凭证才证明applied；协商后的outcome必须贯穿每跳校验，非法值不能静默降级为旧close。旧close、取消和失联分别结算，source、资源跟踪和读者能力独立，不改写旧live绑定或以新协议版本替旧provider补证。能力及幂等回执边界未定时不启用生产接口。

有限模型的每个负例与能力组合须独立状态/trace，不能首个fault后跳过剩余分支仍报整组通过。诊断预算从spawn前单调时钟计入setup，显式分开synthetic和真实进程证据；受控后代私有回执和有限TTL只用于夹具观察，不提供按日志PID强杀权限，也不新增产品后代托管义务。

故障注入须同时记录载体和性质：真实进程执行native替身不等于系统调用真实失败，通知扣留不等于API卡住，有限模型不等于资源已释放。准入上限与unknown熔断限制继续积累，但不隔离共享地址空间的卡死或崩溃；每会话隔离必须在创建前安排，不能事后迁移未知owner。

返回预算的证据应来自调用方实际await续体及独立观察，不用resolve前日志代替。等待API结算、进程退出和证据落盘分别计时、分别验收；写盘失败不撤销已经确认的返回，也不能把未封存工件报告为完整证据。

独立重放必须只用当时已收到的事实推导首次报告，迟到错误不能回溯改写首报。完整owner台账和准入封禁也要从原始责任重建，不能只核最终kind。到期才冻结的超时报告不可能被消费者在原deadline前观察到；消费预算未定时应显式未闭合，不暗加宽限或伪报及时。

证据的hash自洽不等于语义可信。命令、预期、负例说明、报告与子manifest均应对齐可信输入和独立复算；标识允许分隔符时，复合key必须使用无歧义tuple编码。初轮绿色漏掉的碰撞或sidecar篡改覆盖要单独补证，不能追认历史通过已经覆盖。

## 8. 不属于空间关系的信息应优先离开画布



当某个按钮、说明或状态并不需要依赖节点位置一起理解时，应优先放到 VSCode 原生侧栏、命令入口或工具栏，而不是继续占用画布固定角落。画布应优先留给节点本体、关系和导航。

## 9. 主工作面应保留稳定回路

如果一个全局主工作面必须长期和用户的高频编辑路径争抢同一宿主区域，就不应把“切回去的成本”默认转嫁给用户。只要 VSCode 提供多个合适的宿主承载面，设计就应优先考虑让主工作面保留稳定、可预测的返回路径。

## 10. 先定义谁拥有长期运行时

如果产品要承诺“关闭画布甚至关闭 VSCode 后，会话仍继续存在”，就必须先写清楚谁拥有进程、谁负责日志、谁负责清理。不要把“快照恢复”误写成“真实进程延续”。

## 11. 第一版默认追求尽量完整实现

第一版不应默认被设计成“只证明可行”的半链路。只有在 blocker、外部依赖边界或暂不支持的平台已经被明确记录时，才允许把能力后移；否则应尽量完整实现产品主张，而不是主动把关键链路拆到后续版本。

## 12. 对象关系与文件活动优先使用结构化事件

只要某个关系或活动需要长期进入画布权威状态，就应优先使用宿主或 provider 的结构化事件，而不是从 PTY 输出、自然语言摘要或视觉文本里反推。猜测可以作为临时诊断线索，但不能冒充正式数据源。

## 13. 安装期聚合不应冒充运行时硬依赖

如果某个能力只是希望“随主产品一起安装”，但主产品在缺少该能力时仍有明确降级路径，就应把安装期聚合和运行时依赖分开表达。不要为了获得一键安装体验，把可选 companion 错写成对称的功能依赖，更不要制造会被平台判定为循环依赖的 manifest 关系。

## 14. 高频原生肌肉记忆不应被画布重写

当画布承载 VSCode 用户已经熟悉的高频原生能力时，应优先复用原生产品语义，尤其是终端里的复制、粘贴、打断、选择和焦点规则。若为了画布一致性偏离原生行为，必须先写清楚会破坏哪类肌肉记忆、为什么值得破坏，以及用户如何发现并理解这个差异。

## 15. 相似词不能复用既有语义

当一个新动作和既有动作在中文里都可叫“恢复”时，代码、协议和文档必须先区分真实对象。例如 provider session `resume` 表示用会话身份恢复历史会话；如果某个 live process 场景缺少可验证的前台恢复语义，就不能只因为 provider 文案提示“恢复”而新增同名动作。同样，恢复已有会话与重启新进程必须使用不同的可见动作语义，不能因为共用按钮组件就共用文案。不要为了文案一致性牺牲状态机边界。

## 16. 高频恢复工作不能压过交互

当系统同时需要处理用户输入、可见输出、恢复快照、诊断和派生上下文时，用户输入与当前可见输出优先；恢复、诊断、链接上下文和兼容 fallback 必须能让步、分批或静默化，除非它们正处在明确的正确性边界上。

## 17. 控制消息不能被数据洪峰淹没

当同一消息通道同时承载高频数据和交互控制信号时，控制信号应有独立的优先路径或明确的分批预算。不要假设接收端限流就足以保护 ACK、错误、生命周期和用户操作反馈。

## 18. 呈现模式不能新增事实源

当一个新交互只是为了帮助用户观察同一批对象，例如 gallery、focus、thumbnail 或其他视图模式时，它应优先作为呈现层状态，而不是新增业务事实源。若必须新增持久化状态，必须先写清它和原有事实源的同步、冲突和恢复边界。

## 19. 发布输入不能混入发布后证据

版本号、用户 release notes、Marketplace 文案和发布契约必须在发布前成为 tag 的不可变输入。工件 hash、渠道结果、workflow run 和门禁执行结果只在发布后 manifest / Release assets 中记录。不要通过修改已发布版本的 CHANGELOG 或再开 PR，把发布后事实伪装成原始发布输入。

截止时的首次观察必须不可变，迟到补证追加而非改写；调用方收到结果、进程退出、真实输出结束和证据归档分别证明。完整保存失败或截断前缀不等于源完整，写入者的成功声明不等于独立校验通过；最终发布故障也不能回写已经交付的首报。

首报冻结和消费者实际收到应独立核验。独立交付窗口不能改写原操作截止或把迟到首报变为及时；同样，负例被拒绝不代表原定类别已被覆盖，保存输入和具体变换须与可信fixture绑定。记录容量耗尽后的证据不可验证应明确失败，而不是以预期故障为由宣称完整归档。

归档中的生产者绝对路径是身份，不是当前机器可打开的地址。跨OS离线验证应分离逻辑路径和受约束的本地成员读取，保留链接原始字节；合成平台元数据只能验证工具规则，不能代替真实junction、权限或打包传输证据。容量条数有界不代表总字节有界，精确邻界不可达时应给出上界或步长证明，不伪造已执行覆盖。
