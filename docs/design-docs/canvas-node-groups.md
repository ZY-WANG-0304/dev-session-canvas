# 画布节点分组设计

## 1. 背景

当前 DevSessionCanvas 已经支持 `Agent`、`Terminal`、`Note`、文件活动节点和通用关系连线。连线可以表达节点之间的关系，但当画布开始承载多个并行 Agent、辅助终端和说明 Note 时，用户还需要一种更粗粒度的空间组织方式，把多个不同类型节点收束到同一个可命名区域里。

这个能力直接服务产品主张中的“多 Agent 协作全局视角”：分组应帮助用户看清哪些节点属于同一个任务阶段、同一个子问题或同一个上下文簇，而不是引入独立白板产品里的复杂对象系统。

## 2. 问题定义

本设计需要回答以下问题：

1. 分组应是节点的一种、节点的父容器，还是单独的画布组织对象。
2. 分组成员关系应显式持久化，还是只通过空间覆盖关系临时推断。
3. 分组移动、成员移动、取消分组和删除分组应如何避免误删正在运行的执行节点。
4. 拖拽入组 / 移出、分组移动和 resize 如何先抽象为基础法则，再由宿主稳定推导归属、扩容、挤走和最终合法状态。
5. 分组如何与现有宿主权威状态、React Flow 渲染、节点绝对坐标、连线、模板和文件活动节点共存。
6. 首版应限制哪些复杂能力，避免一次性引入交叉分组、折叠、自动布局和执行节点隐藏带来的风险。

## 3. 目标

- 允许用户创建空分组，也允许用户把多个不同类型的稳定画布节点纳入同一个可命名分组。
- 允许用户把稳定节点拖入分组区域；入组条件是鼠标释放位置落在目标分组框内，目标为该位置所在的唯一最内层可容纳分组，不要求被拖拽对象已经完全落在分组边界内。
- 支持分组嵌套，但不支持分组交叉；任意两个分组只能互不相交或严格包含。
- 分组进入宿主权威状态，并在 reload、窗口重开和模板应用后保持。
- 分组移动可以批量移动直接成员节点和内部子分组，并在拖到画布边缘时像节点拖动一样带动画布平移；它不会改变节点本身的执行会话、Note 内容或连线事实。
- 分组视觉语言跟随 VSCode 主题和现有低噪音工作台风格。
- 首版支持嵌套分组，但不引入折叠、交叉分组、组级连线或自动布局。

## 4. 非目标

- 不把分组做成新的执行节点类型。
- 不在首版支持分组交叉、折叠隐藏、泳道、自动布局或批量运行；后续版本也没有计划支持折叠分组。
- 不允许关系线直接连接分组框；关系线仍连接具体节点。
- 不把自动文件活动节点作为首版稳定分组成员。
- 不把分组当作权限、分享、跨 workspace 同步或发布单位。
- 不在首版提供分组颜色自定义；分组视觉只使用统一的 VSCode theme token 表达。

## 5. 行业成熟方案调研

### 5.1 React Flow：父子节点 / sub flow

React Flow 官方把 sub flow 描述为“节点里的 flow”，也明确说明该能力可以用于节点分组。成熟机制包括：父节点必须先于子节点出现在 `nodes` 数组中；子节点通过 `parentId` 挂到父节点；子节点坐标相对父节点；`extent: 'parent'` 可以限制子节点不能移出父节点；内置 `group` 节点类型没有 handles，适合作为纯容器。

这说明 React Flow 已经提供成熟的父子渲染与拖拽模型，但它的默认心智是“子节点坐标相对父节点”。当前仓库的宿主权威状态和连线锚点都以节点绝对坐标为基础，如果直接把持久状态切到 React Flow 父子坐标，会牵动 `moveNode`、`resizeNode`、边锚点、模板落位和文件活动重建等多处逻辑。

参考：<https://reactflow.dev/learn/layouting/sub-flows>

### 5.2 Figma：Group、Frame、Section 分工

Figma 把 `Group` 和 `Frame` 区分得很清楚：Group 会采用子图层的合并边界，子图层移动后 group bounds 自动跟随；Frame 则是用户显式设定尺寸的容器，可以通过拖入 / 拖出管理内容；Section 进一步服务画布区域标注和组织。

对 DevSessionCanvas 的启发是：如果用户要的是“批量选择与逻辑组合”，自动边界 group 更轻；如果用户要的是“可命名工作区域”，显式尺寸的 frame / section 更符合空间组织。当前需求更接近后者，因为用户希望把多个节点放到同一个可见分组中，而不仅是临时把几个对象当成一个选择集合。

参考：<https://help.figma.com/hc/en-us/articles/360039832054-The-difference-between-frames-and-groups>、<https://help.figma.com/hc/en-us/articles/9771500257687-Organize-your-canvas-with-sections>

### 5.3 Miro：Frame 是可索引、可导航的父容器

Miro 的 Frame 用来组织 board 内容、重命名、调整尺寸、导出和演示。Miro 开发文档中，Frame 是可以包含 child items 的 parent item；子项坐标相对于 frame 左上角。这是一套成熟的“容器即导航单位”模型。

对 DevSessionCanvas 的启发是：分组不必只服务批量拖拽；它也可以成为用户回到某个工作区域的导航锚点。但当前产品仍应避免把分组升级成演示页或导出页，因为 DevSessionCanvas 的主路径是 VSCode 内的开发工作台，而不是通用白板。

参考：<https://help.miro.com/hc/en-us/articles/360018261813-Frames>、<https://developers.miro.com/docs/frame-1>

### 5.4 tldraw：逻辑 Group 与可见 Frame 分层

`tldraw` 官方把 Groups 定义为无视觉表现的逻辑容器：几何边界来自子对象并自动更新，内容删除后 group 会清理自身，也支持嵌套。其默认 shapes 文档又把 Frame 描述为会裁剪内容、移动 frame 时内部形状跟随移动的可见容器。

对 DevSessionCanvas 的启发是：逻辑 group 和可见 frame 解决的是不同问题。当前需求要让用户“看见一组节点属于同一区域”，因此不应只做无视觉的逻辑 group；但 tldraw 的自动清理、取消分组和子对象仍可单独选中等行为值得借鉴。

参考：<https://tldraw.dev/sdk-features/groups>、<https://tldraw.dev/sdk-features/default-shapes>

### 5.5 JSON Canvas / Obsidian Canvas：Group 作为视觉区域节点

JSON Canvas 规范把 `group` 列为一种 canvas node，拥有 `x`、`y`、`width`、`height`、可选 `color` 和 `label`。它没有把成员列表作为 group 的必备字段，这更接近“视觉区域标注”而不是严格父子关系。

对 DevSessionCanvas 的启发是：视觉 group 的最小数据结构可以很轻，但如果只依靠几何覆盖推断成员关系，就无法稳定满足“多个节点属于同一个分组”的产品语义，也会让 reload、模板和批量移动的结果难以解释。

参考：<https://jsoncanvas.org/spec/1.0/>

### 5.6 调研结论

成熟产品和库基本收敛到两类模型：

1. 逻辑 group：无固定视觉或自动跟随子对象边界，适合一次性把对象当成单个选择单元。
2. 可见 frame / section：有显式边界、标题和尺寸，适合在无限画布上组织区域、导航和演示。

DevSessionCanvas 的首版分组应采用“可见 frame + 显式成员关系”的混合方案：用 frame 的视觉和交互降低空间理解成本，用显式成员关系满足批量移动、嵌套、持久化和模板恢复；不要采用纯视觉覆盖推断，也不要一开始引入交叉分组与折叠。

## 6. 候选方案

### 6.1 方案 A：把分组作为 `CanvasNodeKind = 'group'` 并直接使用 React Flow parent-child

做法是新增一种 group 节点，成员节点在 React Flow 中使用 `parentId`，位置改为相对 group，必要时设置 `extent: 'parent'`。

优点：

- 最贴近 React Flow 官方 sub flow 模型。
- 父节点移动带动子节点、子节点限制在父节点内等行为由底层库承担。
- Webview 侧拖拽和选择能复用较多现成能力。

风险：

- 当前 `CanvasNodeSummary.position` 是宿主权威绝对坐标，直接改成相对坐标会牵动持久化、边锚点、模板、文件活动节点和节点避碰。
- 把 group 放进 `CanvasNodeKind` 容易污染“节点就是协作对象或文件活动对象”的语义；group 没有状态、summary、execution metadata，也不应出现在执行节点列表里。
- React Flow 的 parent-child 渲染要求父节点先于子节点排序，现有状态同步和 template 物化需要额外排序不变量。

当前判断：暂不作为首版推荐，除非后续验证证明自定义 group frame 交互成本明显高于坐标迁移成本。

### 6.2 方案 B：新增 `CanvasGroupSummary`，节点保留绝对坐标和可选 `groupId`

做法是在共享协议中新增独立 `groups` 集合，在稳定节点上保存可选 `groupId`，并在分组上保存可选 `parentGroupId`。分组框有自己的绝对位置和尺寸；成员节点与分组仍保留当前绝对坐标。Webview 负责把分组框渲染在节点下方，宿主负责创建、更新、移动、删除、嵌套和清理成员关系。

优点：

- 保留当前宿主权威状态和绝对坐标模型，避免一次性重写边锚点和节点移动语义。
- group 不进入 `CanvasNodeKind`，不会被误认为执行对象、文件活动对象或普通 Node 列表项。
- 显式成员关系能稳定支持 reload、模板保存 / 应用和批量移动。
- 首版通过 `parentGroupId` 支持分组嵌套；未来若要升级到 React Flow parent-child，协议中 `groups`、`parentGroupId` 与 `groupId` 仍能作为迁移输入。

风险：

- Webview 需要自定义分组框拖拽、调整尺寸、选中和命中层级，不能完全依赖 React Flow 内置 group node。
- 分组移动需要宿主以一个事务同时更新 group、所有直接成员节点和内部子分组，避免多个 `moveNode` 消息造成中间状态闪烁。
- 如果后续要做严格裁剪或 parent-relative 坐标，仍需再设计坐标迁移。

当前判断：作为首版推荐方案，但仍需通过 Webview spike 验证命中层级、嵌套拖拽、移动 / resize 后的交叉消解和 group drag 不破坏节点内部终端、Note 与连线交互。

### 6.3 方案 C：仅做 JSON Canvas 风格视觉分组，不保存成员关系

做法是把 group 当成一个有标题的背景框，节点是否“属于”它只由视觉覆盖或用户心智决定。

优点：

- 状态结构最小，几乎不影响节点模型。
- 视觉上可以快速提供区域标注。

不选原因：

- 不能可靠支持“把多个节点放到同一个分组中”的语义。
- 批量移动、取消分组、模板应用和 reload 后成员解释都不稳定。
- 与仓库“宿主权威状态必须承载长期事实”的原则冲突。

### 6.4 方案 D：无视觉逻辑 group，边界自动来自成员节点

做法类似 tldraw logical group：创建后作为单个选择单位，bounds 自动由成员节点合成，不显示长期区域框。

优点：

- 适合批量移动和临时组合。
- 自动 bounds 不需要用户维护分组尺寸。

不选原因：

- 用户无法在画布上持续看见“这些节点属于同一工作区域”。
- 对 DevSessionCanvas 的核心价值“全局可见性”帮助不足。
- 后续若再补可见区域，仍会回到 frame / section 模型。

## 7. 风险与取舍

- 取舍：首版采用可见分组框，而不是无视觉逻辑 group。
  原因：DevSessionCanvas 的分组主要服务空间理解和区域命名，而不是临时选择集合。

- 取舍：首版使用独立 `CanvasGroupSummary`，不把 group 加进 `CanvasNodeKind`。
  原因：当前节点类型均代表用户可操作的协作对象或文件活动对象；group 是组织结构，不应承担节点状态、执行会话或文件活动语义。

- 取舍：首版保留成员节点绝对坐标。
  原因：现有 `CanvasPanelManager`、边锚点、模板和文件活动都基于绝对坐标；先保持坐标模型稳定能显著降低回归面。

- 风险：分组框 body 可能遮挡节点选择、连线选择或画布 pan。
  缓解：分组主交互热区优先放在标题栏和边框；body 默认低优先级，不覆盖成员节点命中。

- 风险：`Agent` / `Terminal` 正在运行时被分组移动，可能触发 xterm 尺寸或焦点异常。
  缓解：分组移动只改变绝对坐标，不改变节点尺寸；Webview 拖拽期间使用局部 draft，停止拖拽后一次性提交宿主。

- 风险：拖拽进入分组如果没有清晰命中规则，可能让节点或子分组成员关系不可预测。
  缓解：首版把鼠标释放位置作为拖拽归属的唯一意图输入；节点左上角、中心点或对象是否完全位于目标分组内只参与后续扩容、不变量校验和入组后的局部避让。释放点命中唯一最内层可容纳分组时才表达入组或重新归属，未命中时不自动入组。拖动一个分组时，该分组的内部节点和子分组作为整棵子树跟随移动；释放时计算入组目标时，候选目标必须排除被拖动分组自身及其所有后代分组，避免把一次整体移动误判为自包含或父子环。如果实现阶段仍提供显式“加入某分组”命令，则该命令必须拒绝父子环。节点拖入分组后若与已有同组节点冲突，宿主只平移本次被拖入的节点簇避让已有同组节点，且尽量保持被拖入节点之间的相对位置和原有重叠关系。

- 风险：拖出父分组自动移出可能让用户在整理位置时丢失成员关系。
  缓解：这是产品确认的首版行为，但只由用户释放位置触发；释放点在当前父分组外才表达移出意图，释放点命中外层祖先或其他可容纳分组时重新归属，未命中任何分组时成为根级对象。系统挤走、自动扩容和级联消解导致的越界不触发自动移出，只用于恢复合法状态。

- 风险：允许分组嵌套后，如果分组之间部分重叠，会形成用户难以解释的交叉归属。
  缓解：首版禁止分组交叉；任何分组移动、调整尺寸、拖拽入组或创建操作后的持久化状态都必须保持互不相交或严格包含。交叉消解不逐一穷举几何组合，而是按基础法则处理：用户直接结果优先，只在同一父分组的兄弟集合内做最小合法修复；resize 同时出现交叉和完整包含时，按释放时交叉集合先消解，再纳入释放时已完整包含集合，避免系统修正制造误归属。

- 风险：删除分组新增“一并删除成员节点与子分组”选项后，可能误删正在运行的执行节点。
  缓解：删除分组必须弹出宿主确认对话框，明确列出将删除的成员数量和执行节点风险；按产品确认，“一并删除内部所有节点与子分组”是危险选项，也是默认按钮。

- 风险：分组和文件活动自动节点共存时，自动节点可能被重建导致成员关系悬空。
  缓解：`file` / `file-list` 暂时不支持稳定分组成员关系；normalize 时清理不存在节点或非稳定节点的 groupId。

## 8. 当前结论

当前采用方案 B：`CanvasGroupSummary + CanvasNodeSummary.groupId`，并把分组表现为可见、可命名、可移动的 group frame。2026-05-22 的实现阶段已经通过 Webview harness 验证了 group frame 标题栏、工具栏与 React Flow pane 的基本命中层级，且用宿主状态测试覆盖了核心拖动 / resize 收口；因此方案本身从“比较中”收口为“已选定”。本轮验证已经通过 `npm run typecheck`、协议消息测试、模板测试、`npm run test:canvas-node-groups`、`npm run build` 和 4 条 Webview 分组 Playwright 用例。验证状态仍是“验证中”，因为侧栏分组树、从选择创建分组、删除对话框和更完整的几何合法状态仍只覆盖了首版基础路径，尚未完成真实 VSCode reload smoke 与完整场景矩阵。

根据 2026-05-20 至 2026-05-21 的产品调整，首版从分组状态和交互中移除颜色配置；取消分组固定保留成员节点和内部子分组；删除分组改为宿主确认对话框中的二选一动作，且“一并删除内部所有节点与子分组”是危险选项也是默认按钮；拖拽节点或分组进入分组区域成为首版入组主路径之一；分组支持嵌套但禁止交叉；`file` / `file-list` 暂不支持稳定分组成员关系；侧栏节点列表通过更多按钮提供按分组树折叠展示选项；不支持且不计划支持折叠分组。拖入、拖出、分组移动和 resize 不再按场景逐项罗列，而是按第 8.2.1 节基础法则推导：合法状态是硬约束，拖拽以鼠标释放位置表达归属，resize 以释放边界表达归属，用户直接结果优先，系统只做最小合法修复，最终由宿主在释放鼠标后以一次事务提交。

### 8.1 状态模型

在 `src/common/protocol.ts` 中扩展共享状态：

    export interface CanvasGroupSummary {
      id: string;
      title: string;
      position: CanvasNodePosition;
      size: CanvasNodeFootprint;
      parentGroupId?: string;
    }

    export interface CanvasNodeSummary {
      id: string;
      kind: CanvasNodeKind;
      title: string;
      status: string;
      summary: string;
      position: CanvasNodePosition;
      size: CanvasNodeFootprint;
      groupId?: string;
      metadata?: CanvasNodeMetadata;
    }

    export interface CanvasPrototypeState {
      version: 1;
      updatedAt: string;
      nodes: CanvasNodeSummary[];
      edges: CanvasEdgeSummary[];
      groups: CanvasGroupSummary[];
      nextGroupSequence: number;
      fileReferences: CanvasFileReferenceSummary[];
      suppressedFileActivityEdgeIds: string[];
      suppressedAutomaticFileArtifactNodeIds: string[];
    }

核心不变量：

- `groupId` 首版只允许出现在 `agent`、`terminal`、`note` 节点上。
- 同一个节点最多直接属于一个最小 group；如果节点处在嵌套分组内，外层归属由 group 父链推导。
- 同一个 group 最多直接属于一个父 group；`parentGroupId` 不能形成环。
- 任意两个 group 不能交叉：它们只能互不相交，或一方完全包含另一方；拖拽和 resize 过程中的临时交叉不能进入宿主持久化状态。
- 同一父 group 内，直接成员节点与直接子 group、直接子 group 与直接子 group 在交互结束后的持久化状态中不交叉；直接成员节点之间允许重叠。节点拖入分组时，如果本次被拖入的节点与目标分组内已有直接成员节点重叠，系统优先把本次被拖入的节点作为整体簇平移到最近可用位置；簇内原本重叠的节点保持重叠关系，簇内原本不重叠的节点不被系统改成重叠。
- 分组默认标题编号使用独立的分组序号队列；实现应沿用现有手工节点序号逻辑，但读取分组自己的序号来源，不读取节点序号队列，也不读取可编辑标题文本。`nextGroupSequence` 保存下一次创建分组应使用的编号；旧状态缺失时根据现有 `group-*` ID 前缀安全推导，后续删除或重命名都不降低该序号。
- 节点坐标保持画布绝对坐标，不改成相对 group 坐标。
- 用户普通点击节点只产生单选和原有节点交互；只有按住 Ctrl / Cmd 点击节点时才进入多选增删，再次 Ctrl / Cmd 点击已选节点会取消该节点选择。Shift 不作为首版分组多选入口。
- normalize 时清理不存在 group、非稳定节点、父子环、交叉 group 或重复非法状态；正常交互路径应在提交前调用基础法则收口流程恢复合法状态，包括同级 group 不交叉、直接成员节点与直接子 group 不交叉、成员 / 子 group 被所属 group 完整容纳，以及必要时在同父兄弟集合内做最小合法修复和逐层级联。
- `groups` 缺失的旧状态归一为空数组，不提升 `CanvasPrototypeState.version`。

### 8.2 宿主权威行为

`src/panel/CanvasPanelManager.ts` 新增分组相关状态操作，保持宿主为唯一权威：

#### 8.2.1 拖动 / resize 基础法则

实现不应靠穷举所有拖动和 resize 几何组合来定义行为，而应把每次交互视为“上一个合法状态 + 本次用户意图”的一次宿主状态事务，并按以下基础法则推导结果；若历史场景口径与法则冲突，以法则为准并回到产品讨论。

1. 合法状态法则：宿主提交前必须得到合法状态。合法状态包括 group 树 / 森林无环、对象最多只有一个直接父 group、同级 group 不交叉、直接成员节点与直接子 group 不交叉、直接子 group 之间不交叉、成员 / 子 group 被所属 group 完整容纳；普通直接成员节点之间允许重叠。
2. 意图载体法则：每次用户操作只有一个语义意图载体。拖拽的意图载体是鼠标释放位置；多选节点同时移动时，这批节点在本次移动中被理解为临时整体，所有被选节点共用主鼠标释放位置作为归属意图；resize 的意图载体是释放后的边界；从选择创建分组的意图载体是选择集合。只有意图载体能改变归属，系统修复过程产生的新几何关系不能改变归属。
3. 用户结果优先法则：先应用用户直接操作结果，包括被拖动对象的释放位置、被 resize 分组的释放边界、新建分组的位置和范围。只要不违反硬性合法状态，就不为了修复其他对象而改写这个直接结果。
4. Resize 边界意图法则：resize 真的能表达归属意图；释放边界既可以让不再被完整包含的直接成员 / 子 group 提升到父级，也可以把释放边界内完整包含的同父 group 纳入当前 group。
5. 最小合法修复法则：应用用户意图后若状态不合法，系统只做恢复合法状态所需的最小修复。修复可以移动兄弟 group、扩展父 group、级联到外层，但不能引入新的语义意图。
6. 子树原子法则：group 在移动和被修复时是整棵子树；拖动一个 group 时，其内部节点和子 group 整体跟随。计算入组目标时，候选目标必须排除被拖动 group 自身及其所有后代 group，避免自包含或父子环。
7. 释放收口法则：拖动过程中只有被拖动节点或被拖动 group 子树跟随鼠标移动，其他节点和 group 不动；释放鼠标后，宿主基于本次意图一次性计算最终归属、位置、尺寸、扩容和挤走结果。

- `createGroupFromSelection(nodeIds, groupIds)`：过滤出稳定节点和可移动分组；至少需要 2 个选中对象，单个节点或单个分组不创建外层分组；所有选中对象必须处于同一父级，若分属不同父分组，或同时包含某个分组及其后代对象，则拒绝创建；若选中分组已有内部子树但未同时选中它的后代对象，则允许创建，该分组连同内部子树整体成为新 group 的直接子分组。通过校验后计算外接矩形加 padding，创建带默认标题的 group，并设置成员节点 `groupId` 与子分组 `parentGroupId`；默认标题使用与现有手工节点一致的创建序号递增逻辑，如 `Group 1`、`Group 2`，但分组使用独立于节点的分组序号队列；编号由分组创建序列决定，不按标题文本查找最小可用编号，删除分组后不主动复用旧编号，用户重命名不影响后续默认编号；创建时不强制弹窗命名，后续可单击分组标题区域进入重命名编辑；标题编辑控件先复用现有手工节点标题栏编辑方式和提交 / 取消行为；分组标题编辑清洗逻辑与现有手工节点标题一致，不设置分组专用最大长度限制，仅保留现有通用文本保护；分组标题不允许为空字符串，清空标题并确认时恢复为原标题，新建分组保持默认 `Group N`；手动重命名允许重名，不强制唯一。若新 group 与同父级已有 group 交叉，保留新 group 并挤走同父兄弟 group；创建、移动、resize 使用一致的同级交叉消解语义。
- `createEmptyGroup(position, size)`：创建空 group，用于用户先规划区域再加入节点；空 group 是正式持久化对象，不依赖立即加入成员。空白区创建时默认尺寸为 `360 x 240`，默认标题使用与现有手工节点一致的创建序号递增逻辑，如 `Group 1`、`Group 2`，但分组使用独立于节点的分组序号队列；编号由分组创建序列决定，不按标题文本查找最小可用编号，删除分组后不主动复用旧编号，用户重命名不影响后续默认编号；创建时不强制弹窗命名，后续用户可以单击分组标题区域进入重命名编辑并可 resize；标题编辑控件先复用现有手工节点标题栏编辑方式和提交 / 取消行为；分组标题编辑清洗逻辑与现有手工节点标题一致，不设置分组专用最大长度限制，仅保留现有通用文本保护；分组标题不允许为空字符串，清空标题并确认时恢复为原标题，新建分组保持默认 `Group N`；手动重命名允许重名，不强制唯一。若新 group 与同父级已有 group 交叉，保留新 group 并挤走同父兄弟 group。
- `moveGroup(groupId, delta)`：以一次状态事务更新 group 位置、所有直接成员节点位置和内部子分组位置；嵌套子树整体平移。释放后把被移动 group 作为用户意图锚点交给基础法则收口流程，按第 8.2.1 节基础法则消解同父兄弟交叉、必要时扩容父分组并级联收口；系统修正不改变本次移动表达的归属意图。
- `resizeGroup(groupId, size)`：调整 group 尺寸；首版尺寸最小值只保证分组框可命中和可显示标题，不强制容纳当前成员节点或内部子分组。释放后把新边界、释放时交叉集合和释放时完整包含集合交给基础法则收口流程：先按释放时交叉集合消解同父兄弟交叉，再纳入释放时已完整包含的同父分组；直接成员节点或直接子分组若因用户边界编辑不再被完整包含，则提升到当前 group 的父级。
- `addNodesToGroup(groupId, nodeIds)`：把选中稳定节点加入目标最小 group；若节点已有 group，先从旧 group 移出。入组后基础法则收口流程负责扩容目标 group、消解同父兄弟交叉并保证节点最终被目标 group 完整容纳。
- `addGroupsToGroup(parentGroupId, childGroupIds)`：把选中分组加入父 group；必须拒绝环、拒绝把父分组加入后代分组。入组后基础法则收口流程负责扩容父 group、消解同父兄弟交叉并保证子分组最终被父 group 完整容纳。
- `resolveDroppedObjectGroup(objectId, pointerPosition)`：节点或分组拖拽结束后，根据鼠标释放位置与分组层级决定唯一归属目标；`pointerPosition` 命中的唯一最内层可容纳 group 是加入或重新归属目标，释放点在当前父分组外表示移出当前父分组，释放点不在任何 group 内则成为根级对象。该函数只产生用户归属意图，扩容、挤走和合法状态收口由基础法则收口流程负责。
- `removeNodesFromGroup(nodeIds)`：清空这些节点的 `groupId`，保留节点位置；显式移出和拖拽释放点不命中任何可容纳分组时使用该语义，释放点命中其他可容纳分组时改由 `resolveDroppedObjectGroup` 重新归属。
- `removeGroupsFromParent(groupIds)`：清空这些分组的 `parentGroupId`，保留分组及其内部对象位置；显式移出和拖拽释放点不命中任何可容纳分组时使用该语义，释放点命中其他可容纳分组时改由 `resolveDroppedObjectGroup` 重新归属。
- `ungroup(groupId)`：删除 group，清空直接成员节点 `groupId` 并把直接子分组提升到当前 group 的父分组；所有内部对象保留在当前画布位置。
- `deleteGroup(groupId, mode)`：删除 group；`mode = 'keep-members'` 时只删除当前 group、保留内部节点并提升子分组，`mode = 'delete-members'` 时递归删除内部子分组并按现有节点删除语义逐个删除内部所有成员节点，执行节点必须走当前会话终止与清理路径；删除确认对话框中 `delete-members` 是危险选项，也是默认按钮。
- `deleteCanvasNode`：删除节点时自然清理该节点，不删除 group；若 group 变空，仍保留空 group。
- `deleteCanvasGroup`：删除分组时清理子树关系；保留内部对象时提升内部子分组，递归删除时先处理内部执行节点清理。
- `resetCanvasState`：清空 nodes、edges、groups 和文件活动域状态。

### 8.3 Webview 交互

`src/webview/main.tsx` 负责分组呈现和局部选中态，但不拥有最终成员关系：

- 分组框渲染在背景之上、普通节点之下；标题栏和边框可命中，body 不应挡住成员节点。
- 分组选中态与节点 / 边选中态互斥，选中 group 后显示轻量工具条：加入选中节点、取消分组、删除分组；重命名先复用现有手工节点标题栏编辑方式，用户单击 group 标题区域即可进入编辑，不单独要求双击或打开命名弹窗。
- 在画布空白区域可以通过右键上下文菜单创建默认 `360 x 240` 的空分组；命令面板可作为补充入口；节点菜单不提供创建空分组入口。多选至少两个同一父级下的稳定对象后，通过上下文菜单或命令面板创建带成员分组；单个节点或单个分组不提供“创建分组”入口；若选中对象分属不同父分组，或同时包含某个分组及其后代对象，入口不可用或宿主拒绝提交；若选中对象包含已有子树的分组但未同时选中它的后代对象，入口可用，宿主把该分组连同内部子树整体纳入新分组。首版不提供默认分组快捷键，因此不绑定 `Ctrl/Cmd+G`、`Shift+Ctrl/Cmd+G` 或其他快捷键；取消分组通过选中 group 后的工具条、上下文菜单或命令面板触发。若创建出的新分组与同父级已有分组交叉，宿主保留新分组并挤走同父兄弟分组。
- 拖动 group 标题栏或边框时，Webview 使用 draft 同步显示 group 与成员节点的移动结果；拖拽结束后发送一次 `webview/moveGroup`，并以宿主返回的统一收口结果为准同步位置、尺寸和归属变化。
- 调整 group 尺寸只改变分组框，不缩放成员节点；首版不因直接子分组外接矩形钳制父分组尺寸。resize 过程中 Webview 只展示草稿边界，释放后由宿主按第 8.2.1 节基础法则决定成员提升、同父分组纳入、碰撞消解和父级扩容。
- 节点或分组普通拖拽结束时，Webview 把鼠标释放位置和对象最终几何信息发送给宿主；多选节点同时移动时，Webview 仍提交每个被选节点的最终位置，但所有被选节点共用主鼠标释放位置作为本次临时整体移动的归属意图；最终 `groupId` / `parentGroupId`、目标分组扩容和碰撞消解都以宿主按第 8.2.1 节基础法则返回的结果为准。
- 拖拽归属命中只看鼠标释放位置：释放点命中唯一最内层可容纳 group 时才表达入组或重新归属；释放点未命中任何 group 时，即使对象矩形与分组部分重叠，也不自动入组。
- 分组拖入另一个分组区域时，同样以鼠标释放位置作为归属命中输入；如果宿主判定形成父子关系，基础法则收口流程负责扩容父分组并保证合法状态。
- 拖动一个分组时，分组内部节点和子分组作为整棵子树跟随移动；释放时计算入组目标时，候选目标排除被拖动分组自身及其所有后代分组，因此不会因为拖动分组本身形成自包含或父子环。如果后续实现提供非拖动的显式分组归属命令，宿主仍必须拒绝父子环，并按基础法则保证最终状态合法。
- 节点或子分组拖出、重新归属、resize 后成员提升、系统挤走和父级扩容都由宿主统一收口；Webview 不在本地把临时交叉、越界或扩容结果继续解释成新的用户意图。

### 8.4 连线、模板和侧栏边界

- `CanvasEdgeSummary` 不引用 group，连线仍连接具体节点。
- 分组移动后，由于成员节点绝对坐标随之变化，连线端点自然跟随；不需要引入组级边锚点。
- `src/common/canvasTemplates.ts` 保存模板时，应保存由模板兼容节点组成的 group 树，并在应用时重建 group id、`parentGroupId` 与成员 `groupId` 映射。
- 自动文件活动节点暂时不支持稳定分组成员关系；保存模板时也不保存包含这类节点的 group 成员关系。
- 侧栏节点列表增加一个“更多”icon 按钮，提供“按分组树折叠展示”选项；该选项只改变侧栏列表呈现，不改变画布分组状态。

## 10. 已确认口径

已确认：

- 拖动与 resize 行为按第 8.2.1 节基础法则推导；如果历史场景口径与基础法则冲突，以基础法则为准并回到产品讨论。
- Resize 真的能表达归属意图；直接成员或直接子 group 不再被释放边界完整包含时提升到父级，释放边界完整包含的同父 group 可被纳入。
- 直接成员节点与直接子 group 不交叉是硬不变量；同级 group 不交叉、直接子 group 之间不交叉、成员 / 子 group 被所属 group 完整容纳也都是最终合法状态要求。普通直接成员节点之间允许重叠。
- 用户结果优先；被拖动对象的释放位置、被 resize 分组的释放边界、新建分组的位置和范围优先保留，系统只做恢复合法状态所需的最小修复。
- 拖动过程中只有被拖动节点或被拖动 group 子树跟随鼠标移动，其他节点和 group 不动；释放鼠标后，宿主一次性处理其他 group 和节点并提交最终结果。
- `file` / `file-list` 自动文件活动节点暂时不支持稳定分组成员关系。
- 侧栏节点列表增加一个“更多”icon 按钮，提供按分组树折叠展示的选项。
- 不支持折叠分组，后续版本也没有计划支持折叠分组。
- 不支持给 group 绑定专用说明 Note；分组只通过标题表达区域语义，说明内容使用普通 `Note` 节点承载。
- 新建分组默认标题使用与现有手工节点一致的创建序号递增逻辑，如 `Group 1`、`Group 2`，但分组使用独立于节点的分组序号队列；编号由分组创建序列决定，不按标题文本查找最小可用编号，删除分组后不主动复用旧编号，用户重命名不影响后续默认编号；创建时不强制弹窗命名，用户后续可单击分组标题区域进入重命名编辑；标题编辑控件先复用现有手工节点标题栏编辑方式和提交 / 取消行为；分组标题编辑清洗逻辑与现有手工节点标题一致，不设置分组专用最大长度限制，仅保留现有通用文本保护；分组标题不允许为空字符串，清空标题并确认时恢复为原标题，新建分组保持默认 `Group N`；手动重命名允许重名，不强制唯一。
- 空白区创建空分组时默认尺寸为 `360 x 240`，后续允许用户 resize。
- 创建空分组主入口为画布空白区右键菜单，命令面板作为补充入口，节点菜单不提供该入口；从选中对象创建分组通过上下文菜单或命令面板触发；首版不提供默认分组快捷键。
- 从选中对象创建分组时，选中对象必须至少有 2 个且处于同一父级；单个节点或单个分组不提供“创建分组”，用户需要容器时应创建空分组再拖入对象；若对象分属不同父分组，或同时包含某个分组及其后代对象，禁止创建分组；若选中对象包含已有子树的分组但未同时选中它的后代对象，允许创建，该分组连同内部子树整体成为新分组的直接子分组。
- 创建空分组或从选中对象创建分组时，如果新分组与同父级已有分组交叉，保留新分组位置，并按基础法则消解同级交叉。
- 删除分组确认对话框中，“一并删除内部所有节点与子分组”是危险选项，也是默认按钮。
