## 目标与全局图景

用户希望在 DevSessionCanvas 的同一张画布里，把多个不同节点放入同一个分组。设计完成后，协作者可以在正式文档中看到：行业成熟方案如何处理 group / frame / section，当前仓库为什么不直接照搬 React Flow parent-child 持久模型，首版应支持哪些行为，以及实现前还需要验证哪些风险。

本计划完成后的可观察结果是：仓库新增分组功能产品规格、分组功能设计文档，并同步设计文档索引与产品规格索引。

## 意外与发现

- 观察：当前仓库已经有通用 edge 模型，边锚点和节点落位都基于 `CanvasNodeSummary.position` 的绝对坐标。
  证据：`src/common/protocol.ts` 中 `CanvasNodeSummary` 直接保存 `position` / `size`，`CanvasEdgeSummary` 保存节点 id 与四向锚点；`src/panel/CanvasPanelManager.ts` 的 `moveNode` / `resizeNode` 直接更新节点绝对位置。

- 观察：React Flow 已提供 parent-child / sub flow 能力，但当前依赖为 `reactflow@11.11.4`，本地类型里同时支持 `parentNode` 与 `parentId`，且 `parentNode` 已标为 deprecated。
  证据：`package.json` 依赖 `reactflow: 11.11.4`；`node_modules/@reactflow/core/dist/esm/types/nodes.d.ts` 包含 `parentNode?: string`、`parentId?: string`、`extent?: 'parent' | CoordinateExtent`、`expandParent?: boolean`。

- 观察：成熟画布工具把“逻辑 group”和“可见 frame / section”分开处理。DevSessionCanvas 的需求更接近可见工作区域，但又需要显式成员关系来支持批量移动和恢复。
  证据：Figma 区分 groups、frames 和 sections；Miro frame 是 parent item；tldraw group 无视觉而 frame 可见；JSON Canvas group 是视觉区域节点但不定义成员列表。

## 决策记录

- 决策：将本轮文档状态标为“比较中 / 未验证”，而不是直接写成已选定。
  理由：虽然当前推荐方案明确，但尚未完成 Webview 命中层级与 group drag spike；仓库约定要求不要把未验证实现细节写成正式结论。
  日期/作者：2026-05-19 / Codex

- 决策：推荐首版采用 `CanvasGroupSummary + CanvasNodeSummary.groupId`，而不是直接新增 `CanvasNodeKind = 'group'`。
  理由：group 是空间组织对象，不应承担节点状态、执行会话或文件活动语义；保留节点绝对坐标可以降低对现有 edge、template、file activity 和持久化路径的回归风险。
  日期/作者：2026-05-19 / Codex

- 决策：首版只把 `agent`、`terminal`、`note` 作为稳定分组成员。
  理由：`file` / `file-list` 是自动文件活动投影，生命周期由宿主重建逻辑决定；若直接持久化为 group 成员，容易产生悬空成员和误导性恢复。
  日期/作者：2026-05-19 / Codex

- 决策：取消分组固定保留成员节点，删除分组则改为确认对话框中的二选一动作。
  理由：取消分组是纯组织结构移除，不应删除执行会话；删除分组属于更强的破坏性动作，用户明确要求可选择一并删除成员，因此需要宿主确认对话框区分“仅删除分组并保留节点”和“一并删除成员节点”。
  日期/作者：2026-05-20 / Codex

- 决策：分组首版不提供颜色配置。
  理由：颜色不是当前分组成立条件，移除该能力可以减少状态字段、工具条动作和视觉配置复杂度。
  日期/作者：2026-05-20 / Codex

- 决策：拖拽节点或子分组进入分组区域时，入组条件是鼠标释放位置落在目标分组框内；不要求被拖拽对象完全位于目标分组边界内。入组后若对象未完全位于目标分组内，自动扩大目标分组必要边界。
  理由：用户明确纠正该规则；鼠标释放位置表达用户想加入哪个分组，自动扩大目标分组能避免出现“属于分组但视觉上在框外”的状态。
  日期/作者：2026-05-20 / Codex

- 决策：入组后目标分组自动扩容复用单侧扩展、不移动原位置和必要时逐层级联挤走同父兄弟分组的规则。
  理由：用户已确认该规则；统一自动扩容行为可以减少实现分叉，并保持入组、系统挤走和父分组扩容的空间结果一致。
  日期/作者：2026-05-20 / Codex

- 决策：用户主动拖出父分组自动移出只看鼠标释放位置是否在父分组外；释放点在外即移出，即使对象矩形仍与原父分组区域部分重叠。
  理由：用户已确认该规则；它与拖拽入组同样以鼠标释放位置表达用户意图，避免用对象矩形覆盖关系产生歧义。
  日期/作者：2026-05-20 / Codex

- 决策：子分组或节点拖出当前父分组后，若释放点落在外层祖先或其他可容纳分组内，则按释放点所在的唯一最内层可容纳分组重新归属；若释放点不在任何分组内，则成为根级对象。
  理由：用户已确认该规则；它把“移出当前父分组”和“按释放点入组”合并为同一次重新归属动作，让嵌套层级调整保持可预测。
  日期/作者：2026-05-20 / Codex

- 决策：普通节点释放点落在当前所属分组的外层祖先分组内时，也从当前最内层分组移出并成为该祖先分组的直接成员。
  理由：用户已确认该规则；普通节点与子分组使用同一套释放点重新归属语义，可以避免节点只能从最内层分组退到根级而不能退到中间祖先层级的异常。
  日期/作者：2026-05-20 / Codex

- 决策：拖动分组时内容整体跟随，不存在形成父子环；用户主动 resize 父分组导致直接成员节点或直接子分组不再被父分组完整包含时，结束后把该对象移出父分组并提升到父分组的父级。
  理由：用户已确认该规则；分组拖动是整棵子树平移，不会把父分组拖入自己的后代。resize 则是用户主动改变父分组边界，边界不再覆盖直接成员节点或直接子分组时应表达为层级移出，而不是强制扩大或拒绝 resize。
  日期/作者：2026-05-20 / Codex

- 决策：同一父分组内，直接成员节点与直接子分组之间、直接子分组与直接子分组之间理论上不存在交叉。
  理由：用户已确认该不变量；这意味着主动 resize 导致对象提升到父级时，正常不会额外产生“移出对象与父级既有直接子分组交叉”的分支，交互和测试应优先保证该不变量。
  日期/作者：2026-05-20 / Codex

- 决策：同一父分组内，普通直接成员节点之间允许重叠。
  理由：用户已确认该规则；普通节点本来可以在无限画布上重叠，首版不因分组能力新增节点间避让或自动排布，只约束直接成员节点与直接子分组、直接子分组之间的交叉。
  日期/作者：2026-05-20 / Codex

- 决策：创建空分组或从选中对象创建分组时，如果新分组与同父级已有分组交叉，保留新分组并挤走同父兄弟分组。
  理由：用户已确认该规则；创建、移动和 resize 都使用同一套同级交叉消解语义，可以减少用户对不同入口行为的额外记忆。
  日期/作者：2026-05-20 / Codex

- 决策：从选中对象创建分组时，如果选中对象分属不同父分组，则禁止创建分组。
  理由：用户已确认该规则；首版只允许把同一父级下的对象组成新分组，避免一次创建分组同时跨层级移动多个对象。
  日期/作者：2026-05-20 / Codex

- 决策：从选中对象创建分组时，如果选中对象同时包含某个分组及其后代对象，则禁止创建分组。
  理由：用户已确认该规则；同时选择祖先分组和后代对象会让同一个对象被既作为子树成员又作为直接成员处理，容易产生重复归属或层级意图不清。
  日期/作者：2026-05-20 / Codex
