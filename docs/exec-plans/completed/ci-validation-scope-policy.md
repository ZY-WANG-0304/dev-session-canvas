# 明确合并 CI 的任务范围与验证复用边界

本 ExecPlan 按 `docs/PLANS.md` 维护。工作目录 `/tmp/dsc-ci-validation-scope`，分支 `docs-ci-validation-scope`，研究基线为 `origin/main@ee4d367c8dd7cf310282a253758d4536b9d7051d`。

## 目标与全局图景

用户要求减少合并 CI 的无效执行，明确必须运行的任务及可省略条件。以 PR #350 代码已通过后仅补文档仍重跑 277 jobs 为具体案例，本轮交付有实际源码和运行证据支持的任务分级设计，区分必须新执行、可以验证后复用、当前变更不适用。运行环境（runner）与验证任务（job/task）分开说明；设计阶段不直接启用未经验证的裁剪策略。

## 意外与发现

`scripts/gates/resolve-plan.mjs::resolvePlan` 比较 `baseSHA` 与真实预合并 `inputSHA`，因此最后一次提交仅为文档不表示整个 PR 都是文档。`taskCatalog` 的无条件基础层还包含所有 regression、前端构建、webview 功能/视觉与市场浏览器任务。当前 `check-acceptance.mjs` 将回执绑定原 input、run/attempt，不能将旧绿色结果直接视为新提交的验收。

## 决策记录

2026-11-01：先做任务范围设计和受控分类验证，交付明确的推荐规则与后续实施验收标准。避免用最后一次提交的路径代替完整 PR 差异，也不将全量结果复用表述为所有任务在新 SHA 上执行过。保留现有发布批次的精确产品来源约束。

## 结果与复盘

设计研究已完成。真实 PR diff 触发 362 tasks / 273 业务 jobs，加上四个控制 jobs 为实际 277；纯文档模型仍为 90 tasks / 8 业务 jobs。文档收口实际运行跨度约 29.18 分钟，Host 两组占累计 job 时间约 85%。推荐先实现普通文档轻量路径和有来源证明的原完整验证复用，再按明确依赖逐步细分模块。文档消费者与 SHA 影响已显式记录；尚未实施 CI 行为变更，缺口登记到技术债跟踪器，不承诺具体收益。

## 上下文与定向

`.github/workflows/release-preflight.yml` 生成 base/head 的实际预合并输入，调用 `ci-validation.yml` 后执行稳定检查 `Verify release contract`。`scripts/gates/resolve-plan.mjs` 决定 functional/artifact 范围，`catalog.mjs::taskCatalog` 枚举任务，`planJobs` 展开矩阵；`check-acceptance.mjs` 和 `github-provenance.mjs` 核实回执及实际 Actions 来源。本轮从这些实现推导规则，不根据文件扩展名或工作流名称直接减项。

## 工作计划

首先对 PR #350 的 `000757e9` 与 `66676236` 以及当前 main 的代表性路径运行现有分类器，统计 task、矩阵 job 和 runner 类型。其次读取两轮 Actions 实际记录，比较变更清单及重跑代价。最后编写设计：轻量必跑门禁、不同变更的验证范围、相同有效输入的原证据复用、必须失效的情形、实施分期与反例验收。

## 具体步骤

在工作目录使用 Node 导入 `buildPlan` / `planJobs`，通过 Git diff 提供真实变更清单；GitHub API 只读取 run/job 数据，保留不含凭据的证据 JSON 到 `docs/references/ci-validation-scope/`。完成后检查 Markdown 链接、设计元数据/索引与 `git diff --check`。

## 验证与验收

报告必须能解释为什么本例最后只改文档仍是全量，以及单独文档 PR 目前实际运行哪些任务。推荐规则必须覆盖无既有成功结果、旧结果失败/取消/缺失、base 变化、代码/锁文件/测试/门禁变化、发布契约和包内文案变化。复用不得冒充新执行；计划内必需任务既无新成功也无有效复用证明时必须拒绝通过。数字区分实际 jobs、目录 tasks 与未来设计目标。

## 幂等性与恢复

只读原工作区与远端 CI，保留用户未跟踪文件。研究脚本不发起发布、修改 ruleset、删除测试或调用市场。文档结果独立记录，现有 CI 按旧策略继续执行。
