# FRONTEND

本文件用于约束用户可见层文档应记录哪些信息。当前不预填具体界面方案，只保留当前项目特别需要描述的维度。

当前 UI design-system 基线见 `docs/UI.md`。本文件继续保留“前端与交互设计需要覆盖哪些维度”的入口职责；具体功能取舍仍进入 `docs/design-docs/`。

## 建议记录维度

- 画布入口与打开方式
- 画布与 VSCode 原生终端、编辑器等宿主能力之间的跳转与回流方式
- 画布的平移、缩放和导航行为
- Agent、终端与 Note 三类当前支持对象的视觉表达
- 对象之间的关系、连接和空间组织方式
- 多对象并行时的视觉层级与信息密度控制
- 选中态、活动态、错误态和完成态的反馈
- Restricted Mode、能力不可用或远程场景下的退化反馈
- 键盘操作、快捷键和可访问性要求
- 小屏幕或窄编辑器宽度下的退化策略
- Webview 隐藏、恢复或 reload 后的界面连续性
- 深浅主题切换下，画布与节点表面如何跟随 VSCode theme token

## 实现检查清单

### 响应式与退化

- 响应式对象是 VSCode 中可变化的 `editor` / `panel` / sidebar 宽度，不是公网网页断点。
- 宽画布应保留 MiniMap、导航控件、节点完整标题栏和当前节点尺寸。
- 中等宽度优先减少非空间性浮层，节点内部通过滚动或裁切保护主内容。
- 窄宽度不应把画布强行改成列表；应依靠 panel / sidebar 布局、MiniMap 和节点聚焦动作恢复上下文。
- sidebar 过窄时，长路径应中间省略，完整值进入 tooltip 或后续详情入口。
- 折叠、移动或暂时离开 sidebar 时，命令面板和画布右键入口仍应保留主路径。
- Webview 隐藏、恢复或 reload 后，宿主权威状态必须能恢复节点、边、尺寸和关键运行时摘要。

### 交互热区与可访问性

- 当前默认服务 VSCode 桌面开发者，不按 touch-first 设计，但按钮和连线仍应有足够热区。
- 导航控件建议保持约 `28px` 热区；普通 action button 至少 `24px` 高；菜单项建议不小于 `24px` 高。
- 连线视觉线可以很细，但交互 hitbox 必须明显大于线宽。
- 所有可点击元素必须有可见 focus 态或宿主原生 focus 行为。
- icon-only 操作必须提供 `aria-label`、`title` 或等价可访问名称。
- 状态不能只靠颜色表达，应有文本、图标或 tooltip 辅助。
- 终端区域获得焦点后，应优先保留 terminal 的键盘语义。

### 运动与反馈

- 动画只用于 attention、Agent `running` 标题栏活性细线、hover / focus transition、菜单显隐和轻量反馈。
- attention 与 Agent `running` 活性动画必须支持 `prefers-reduced-motion`，并在降级后保留非动画视觉提示。
- 不使用大范围页面入场动画、粒子动效或持续背景运动。

### 文档分流

- 如果改变长期产品判断、视觉原则或体验取舍标准，更新 `docs/PRODUCT_SENSE.md`。
- 如果改变跨功能 UI 规则，更新 `docs/UI.md`；如果改变某个功能自己的 palette、页面结构或组件语言，更新对应功能 UI 文档，例如模板市场更新 `docs/marketplace/UI.md`。
- 如果改变某个功能的目标、非目标、候选方案、风险或正式方案，更新 `docs/design-docs/` 对应文档和索引。
- 如果改变用户需求范围或验收口径，更新 `docs/product-specs/`。
- 涉及 UI / 交互实现时优先补 Playwright Webview 回归；涉及宿主行为时补 VSCode smoke；无法自动化时写明手动验证路径。
- 截图或 Marketplace 媒体只能作为展示结果，不能替代正式设计结论。

### 持续验证关注点

- 高对比主题、极窄 sidebar、远程场景、Restricted Mode 和 Webview reload / restore 需要在具体功能验证中持续补强。
- 不能把常规浅色 / 深色主题通过误写成全平台完成。
- 如果某项 UI 结论只完成视觉截图确认，仍需明确是否缺少宿主行为、键盘路径或可访问性验证。

## 使用原则

- 如果界面方案尚未确定，先写问题、约束和候选方向，不要先写具体 UI 结论。
- 如果只是提出方向，明确标注为“候选方案”或“草案”。
- 任何视觉方案都应先回答“它如何帮助用户看清全局”，再讨论风格。
- 任何需要借助 VSCode 原生能力补全的体验，都应写清用户如何感知“离开画布”和“回到画布”。
- 如果后续形成稳定的画布交互规范，再单独整理到具体设计文档中。
