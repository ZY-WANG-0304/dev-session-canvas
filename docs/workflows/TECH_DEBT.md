# TECH_DEBT

这个文件定义登记、拆解和修复技术债时的工作规则。

## 目的

- 让技术债从发现、登记到修复都能被追溯。
- 避免技术债修复分支变成无边界的顺手重构。
- 允许分批缩小大技术债，同时保护主路径不引入新的债务。

## 登记规则

技术债默认登记到 `docs/exec-plans/tech-debt-tracker.md`。如果某项技术债更适合放在相关 `ExecPlan`、设计文档或产品规格中，也必须能从正式文档追溯到背景、边界和后续修复时机。

登记时至少写清：

- 背景与触发条件
- 影响范围
- 当前临时处理或边界
- 建议修复时机
- 关联文档或代码路径

不要把未确认内容写成已确认事实；无法稳定复现或证据不足的问题，应明确写成风险、缺口或待验证项。

## 修复范围

修复技术债时，代码变更的目的必须只服务于当前要修复的技术债。可以做必要的测试、文档和最小支撑重构，但不能混入与当前技术债无直接关系的顺手修复、风格整理、命名清理、性能优化或其他历史问题。

如果在修复过程中发现新的问题，默认先记录为新的 follow-up 或技术债；只有当它会直接阻止当前技术债修复成立，或当前改动已经引入确定性 regression 时，才纳入本轮修复范围，并在提交或 MR 描述中说明纳入原因。

## 分批收口

大型技术债可以只修复其中一部分，只要本轮能明确降低风险或缩小影响范围。分批修复时必须更新原技术债记录或关联计划，说明：

- 本轮已经收口的部分
- 仍然保留的缺口
- 剩余缺口为什么不阻塞当前合并
- 下一次继续修复的建议触发条件

不要把“部分修复”写成“已经完全解决”。如果原技术债被拆成多个更小问题，应让旧记录指向新的记录或说明拆分结果。

## 新增债务禁止

技术债修复不得引入新的技术债。合并前应确认当前方案没有用新的临时绕过、未记录假设、文档漂移、测试缺口或维护成本换取表面收口。

如果确实存在无法避免的新增风险，本轮不能把它伪装成完成；应优先调整方案，使技术债净减少。只有在项目负责人明确接受新的风险时，才可继续，并必须把新增风险登记到正式文档中。

## 验证与 MR 说明

每次技术债修复至少应包含自动化测试、文档更新或手动验证说明之一。MR 描述应明确写出本轮修复的技术债、实际修复范围、验证结果和剩余风险；如果只完成部分收口，必须明确说明剩余部分的位置。
